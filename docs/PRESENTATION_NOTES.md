# SafeCity — Presentation & Viva Preparation Notes

## 1. Project Objective

SafeCity is a **smart city safety platform** that empowers citizens to report incidents, stay informed, and stay safe — while giving administrators powerful tools to moderate and analyze city-wide safety data.

## 2. Problem Addressed

- Citizens lack a centralized platform to report and view safety incidents
- No visual representation of unsafe areas in a city
- No route planning that considers safety (not just distance/time)
- Administrators lack tools to moderate and analyze incident data
- Emergency response lacks a quick SOS mechanism with location

## 3. Proposed Solution

A full-stack platform with:
- **Web app** (React) for citizens & admins
- **Mobile app** (React Native/Expo) for citizens
- **REST API** (FastAPI) with PostGIS spatial database
- **Safe route planning** using OSRM + incident data
- **Area safety scoring** using severity-weighted incident analysis

## 6. System Architecture Explanation

- **Monorepo** with 3 apps + shared types
- **Layered backend**: Routers → Services → Repositories → Models
- **Stateless JWT auth** with refresh token rotation
- **PostGIS Geography** (SRID 4326) for all spatial data
- **Docker Compose** for deployment (db, backend, web)

## 7. Database Explanation

- **11 tables** with FK relationships
- **6 enum types** (userrole, severitylevel, incidentstatus, notificationtype, alerttype, sosstatus)
- **3 PostGIS geography columns** (incidents, community_alerts, sos_requests)
- **Composite indexes** for common query patterns
- **Soft delete** for incidents (deleted_at)

## 8. Safe Routing Explanation

1. OSRM generates direct route candidates (with alternatives)
2. A "safer alternative" is generated by routing via a perpendicular offset midpoint
3. Each route's polyline is decoded and exact distance calculated via Haversine
4. PostGIS finds approved incidents within 200m of each route
5. Safety score = 100 − (15×critical + 10×high + 5×medium + 2×low)
6. Shortest route = min distance; Safest route = max score (tie-break: shorter)

## 9. Area Safety Index Explanation

1. PostGIS ST_DWithin finds approved incidents within radius
2. Severity weights: LOW=2, MEDIUM=5, HIGH=10, CRITICAL=15
3. Recency multiplier: 7d=1.5x, 30d=1.2x, older=1x
4. Density penalty: >5/km² = −10, >2/km² = −5
5. Score = max(0, 100 − weighted_penalty)
6. Risk level: ≥75 safe, 40–74 moderate, <40 unsafe

## 10. ML Explanation

**No ML model is implemented.** The safety scoring is a **rule-based weighted penalty system**. There is no Random Forest, neural network, or any ML library in the codebase.

## 11. Geospatial Technology Explanation

- **PostGIS Geography type** (SRID 4326) — accurate great-circle distance calculations
- **ST_DWithin** — radius-based spatial queries using GiST index
- **ST_MakePoint / ST_SetSRID** — create points from lat/lng
- **ST_GeomFromText** — create LineString for route safety
- **Geography vs Geometry**: Geography uses meters, Geometry uses degrees

## 14. Major Challenges & Solutions

| Challenge | Solution |
|---|---|
| Spatial queries performance | PostGIS GiST index on geography columns |
| Route safety evaluation | Buffer-based incident proximity (200m) |
| Anonymous reporting | Nullable reporter_id with SET NULL |
| Token expiry | Refresh token rotation |
| Enumeration attacks | Generic OTP responses |
| Image abuse | Extension + size validation, max 5 per incident |

## 15. Limitations Discovered

- No ML model — safety score is rule-based only
- "Safer alternative" route is a simple midpoint offset, not true risk avoidance
- No real-time push (WebSocket/SSE) — polling via React Query
- No audit log table
- No background job queue (Celery/Redis)
- Heatmap weights are simple severity integers
- `new_users_this_month` stat is hardcoded to 0
- Mobile app uses hardcoded default coordinates (not live GPS) for reporting
- No tests found in the repository (pytest in requirements but no test files)

## 17. Likely Viva Questions & Answers

### Q: Why PostGIS?
**A**: PostGIS adds spatial data types and spatial indexes (GiST) to PostgreSQL. SafeCity needs radius-based queries ("find incidents within 1km") which would require full table scans with plain lat/lng columns. With PostGIS `ST_DWithin` on a Geography column, the query uses a spatial index for fast lookups, and Geography type gives accurate meter-based great-circle distances.

### Q: Why OSRM?
**A**: OSRM (Open Source Routing Machine) is free, open-source, and based on OpenStreetMap data. It provides realistic driving routes with alternatives without API keys or usage costs. Alternatives like Google Maps Directions API require billing and have usage limits.

### Q: Why OpenStreetMap?
**A**: OSM tiles are free, don't require API keys, and work with Leaflet. Combined with OSRM (which also uses OSM data), the entire mapping stack is open-source with no vendor lock-in.

### Q: Why Random Forest? (Trick question)
**A**: Random Forest is **not implemented** in SafeCity. The safety score is a deterministic rule-based weighted penalty system. If asked about ML, clarify that the current implementation uses severity weights, recency multipliers, and density penalties — no ML model exists in the codebase.

### Q: How is route safety calculated?
**A**: Each route's polyline is decoded into coordinates. A PostGIS LineString is built from them, and `ST_DWithin` finds approved incidents within 200m. The score starts at 100 and deducts 15/10/5/2 points per critical/high/medium/low incident respectively, capped at 0.

### Q: How is area safety calculated?
**A**: `ST_DWithin` finds approved incidents within the radius. Each incident contributes a severity weight (2/5/10/15) multiplied by a recency factor (1.5x if <7 days, 1.2x if <30 days). The total penalty is subtracted from 100, plus a density penalty if incidents/km² exceeds thresholds.

### Q: How are incidents mapped?
**A**: Each incident stores `location_lat`, `location_lng`, and a PostGIS `location_geom` geography point. The frontend fetches incidents (list or nearby) and renders them as Leaflet markers with severity-based colors, or as a heatmap using severity weights.

### Q: How are unsafe areas identified?
**A**: By the area safety score. Any area with score < 75 is "moderate", < 40 is "unsafe". The map shows a score panel when the user clicks a location, and the city overview shows the overall score.

### Q: How does SOS work?
**A**: The user triggers SOS with their GPS coordinates. The backend creates an `sos_requests` record with status=active and a PostGIS point. Only one active SOS per user is allowed. The user (or system) resolves it via PATCH with status=resolved or false_alarm, which sets `resolved_at`.

### Q: How is authentication handled?
**A**: JWT-based. Login returns an access token (30 min) and refresh token (7 days), both HS256-signed with `type` claims. The frontend attaches the access token as a Bearer header. On 401, the Axios interceptor calls `/auth/refresh` to get new tokens. Passwords are bcrypt-hashed.

### Q: How are audit logs handled?
**A**: **There is no dedicated audit log table.** The closest is the `admin_note` field on incidents and the soft-delete `deleted_at` timestamp. Admin actions are not systematically logged.

### Q: How is user data protected?
**A**: Passwords are bcrypt-hashed (never stored in plaintext). OTPs are bcrypt-hashed. Tokens are signed JWTs. CORS restricts origins. File uploads are validated. Anonymous reporting hides reporter identity (reporter_id set to NULL).

### Q: How does the frontend communicate with the backend?
**A**: Via REST over HTTP using Axios. The web app uses a shared Axios instance with request/response interceptors (attach token, handle 401 refresh). React Query manages caching and invalidation. The mobile app uses a similar Axios client with a refresh-token queue.

### Q: What is the difference between the shortest and safest route?
**A**: They are genuinely calculated differently. Shortest = minimum Haversine distance across all candidate routes. Safest = maximum safety score (incident-based), with shorter distance as a tie-breaker. The "safest" candidate pool includes an alternative route generated via a midpoint offset to encourage a different path.

### Q: What happens when OSRM is unavailable?
**A**: The code catches the exception and uses a hardcoded fallback polyline with approximate distance/duration, so the API still returns a response (though with degraded accuracy).

### Q: What happens when safety data is unavailable?
**A**: If no incidents are found near a route, the score is 100 (safe). If the database query fails, the exception propagates and the API returns an error. There is no separate safety-data cache.

### Q: How are images stored?
**A**: Uploaded files are saved to the `uploads/` directory with UUID filenames. The URL (`/uploads/{filename}`) is stored in `incident_images`. The backend serves them as static files via FastAPI's StaticFiles.

### Q: How does the heatmap work?
**A**: The `/incidents/heatmap` endpoint returns approved incidents as points with a weight based on severity (low=1, medium=2, high=3, critical=4). The frontend renders these with Leaflet's heatmap plugin, where weight drives intensity.

### Q: What is the OTP flow?
**A**: 3 steps: (1) POST email → 6-digit OTP generated with `secrets`, bcrypt-hashed, stored with expiry; email sent via SMTP. (2) POST OTP → verified against hash, max 5 attempts, marks used, returns a 15-min JWT reset token. (3) POST new password + reset token → password updated, OTP records deleted.
